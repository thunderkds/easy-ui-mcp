easy-ui-mcp

A Dockerized MCP server that lets an AI agent such as Claude Code drive a real browser step by step and get back a JSON and HTML report with screenshots.

It exposes 16 tools built on Playwright over HTTP/SSE. Claude Code decides what to click; the server only performs each action, logs it, and writes the report when the session ends. No test scripts to write, and no LLM runs inside the container.

Quick start

  1. 01

    Build and start the container.

    $ docker compose up -d --build
  2. 02

    Check that it is alive.

    $ curl http://localhost:8765/health
# {"status":"ok"}
  3. 03

    Connect Claude Code.

    $ claude mcp add --transport http easy-ui-mcp http://localhost:8765/mcp

Then ask Claude Code to navigate to a page and take a screenshot. It will call the tools below and report back.

Use from another repo

MCP registration is per project: run claude mcp add from that repo's root too. The container only needs to run once and is shared across repos.

$ cd /path/to/your-app
$ claude mcp add --transport http easy-ui-mcp http://localhost:8765/mcp

Networking

The container runs with network_mode: host in docker-compose.yml, not a published port on a bridge network. This is required: the browser Playwright drives inside the container must reach localhost:<port> on your host machine, where the dev server of the app you are testing runs. On a default bridge network the container has no route back to the host, so targets such as http://localhost:8766 hang or fail with ERR_CONNECTION_REFUSED.

Where network_mode: host is not available (for example Docker Desktop on macOS or Windows), use host.docker.internal as the hostname instead of localhost when calling ui_navigate, and add this to docker-compose.yml:

extra_hosts:
  - "host.docker.internal:host-gateway"

Tools

All 16 tools. A session is bracketed by ui_start_session and ui_end_session; the actions in between are logged into the report.

toolpurpose
ui_start_sessionOpen a fresh browser context and start logging into a report.
ui_end_sessionWrite the JSON and HTML report and return their paths.
ui_stepLabel what you are about to do; following actions are grouped under it in the report.
ui_navigateNavigate the browser to a URL.
ui_get_page_stateReturn URL, title, up to 200 visible interactive elements with ready-to-use selectors, and visible alert messages.
ui_take_screenshotCapture the current viewport as a PNG in the reports output.
ui_clickClick the single element matching a selector.
ui_fillFill the single input matching a selector with a value.
ui_select_optionChoose an option of a <select> by value or visible label.
ui_press_keyPress a key or combo such as Enter, Tab, Escape or Control+a, on an element or on whatever has focus.
ui_hoverMove the pointer over an element to reveal hover content such as dropdown menus.
ui_set_checkedSet a checkbox or radio button to checked or unchecked.
ui_scrollScroll an element into view, or the page down by one viewport when no selector is given.
ui_assertHard check of a JS expression: false fails the whole session.
ui_checkSoft check of a JS expression: recorded in the report, the run continues.
ui_wait_forPoll a JS expression until it is true; a timeout fails the session.

Writing a flow

Label your steps

ui_step(label) groups everything that follows under a plain-language heading until the next ui_step. The label is the report's only caller-authored statement of intent. A session with no ui_step calls still renders, under one implicit group.

ui_start_session  target: "Account Access toggle smoke"
ui_step           label:  "Open the Settings page"
ui_navigate       ...
ui_wait_for       ...
ui_step           label:  "Turn Manual Invoice access on"
ui_click          ...
ui_assert         ...
ui_end_session

Use the selector from page state

ui_get_page_state returns each visible interactive element as {role, name, selector}. Every selector is checked against the live page before it is returned, so pass it unchanged to the interaction tools instead of guessing a CSS selector. A selector containing nth= is positional: call ui_get_page_state again after the page changes before reusing it.

{"role": "button", "name": "Sign in", "selector": "[data-testid=\"signin\"]"}
ui_click  selector: [data-testid="signin"]

Verifying vs waiting

A session is marked failed if any hard action fails, so how you verify decides whether the report tells the truth.

toolcondition false meansuse it for
ui_assertThe session fails.A claim about the app: "the toggle is now on".
ui_checkRecorded and shown; the run continues.An observation for the report that should not condemn the run.
ui_wait_forKeeps polling; timing out fails the session.Waiting for the page to render or settle.

Never call ui_assert in a retry loop to wait for something: the first false result permanently fails the run even if the app is fine. That is what ui_wait_for is for. For ui_check and ui_wait_for, a condition that cannot run at all (no page open, or the expression throws) is always a hard failure.

Reports

Reports are written to ./reports/ on the host (the directory is volume-mounted) and named:

session-<YYYYMMDD-HHMMSS>-<slug>-<id8>.{json,html}

That is the UTC start time, a readable slug of the session target, and the first 8 characters of the session id. reports/index.html lists the sessions, newest first and capped at 500 (older reports stay on disk, unlisted), and is rewritten after every report.

An HTML report shows:

  • a verdict box: status, target, step, action and failure counts, and duration;
  • the run as labelled steps, with per-step outcomes and elapsed time;
  • browser problems: console errors, uncaught page errors and network-level request failures, captured automatically and never changing the verdict (up to 50 per session);
  • the raw action log, collapsed behind a disclosure.

HTTP error responses such as 404 or 500 do not trigger Playwright's requestfailed event and are not listed automatically. Auto-failure screenshots are budgeted per session (FAILURE_SCREENSHOT_BUDGET, default 3), and identical screenshot content is embedded only once.

REST wrapper

For callers that cannot speak MCP, POST /api/run-test runs one navigate-and-screenshot test and returns a report. For multi-step flows, drive the MCP tools from Claude Code instead.

$ curl -s -X POST http://localhost:8765/api/run-test \
    -H "Content-Type: application/json" \
    -d '{"app_url_or_package": "https://example.com", "flow_description": "Smoke test", "platform": "web"}'
fieldrequireddescription
app_url_or_packageyesURL to navigate to. Non-empty string, else 400.
flow_descriptionnoLabel for the run in reports. Defaults to the URL.
platformnoOnly "web" is supported in v1; anything else returns 400.
timeoutnoMilliseconds, a positive number. Default 30000.

The response is JSON with status (passed, failed or timeout), report_url, screenshots and logs. report_url is a path inside the container: read the report from the host under ./reports/ using its basename. GET /health returns {"status":"ok"}.

Troubleshooting

symptomlikely causeremediation
"port is already allocated" on docker compose upA stale container from a previous session or worktree holds port 8765.docker ps -a | grep 8765, then docker stop <id> && docker rm <id> and retry.
PORTS column empty in docker compose ps though up -d succeededA transient Docker Compose quirk seen in this environment.docker compose down, then docker compose up -d again (a full cycle, not just up).
npm test hangs or fails with EADDRINUSEPort 8765 is held, usually by the running container: two test files start their own server on that port.docker compose stop, run npm test, then docker compose up -d.
Target localhost URLs hang or give ERR_CONNECTION_REFUSEDThe container is not on the host network, so it cannot reach your dev server.Keep network_mode: host, or use host.docker.internal as described under Networking.
Malformed JSON POST to /mcp returns a raw stack traceThe JSON-parse error handler is missing (fixed in T001).Check the JSON-parse error middleware is registered immediately after express.json() in src/server.ts.

Development

Install dependencies and run the tests locally. npm test needs port 8765 free: stop the Docker container first, because the tests start their own server on that port.

$ npm ci
$ docker compose stop
$ npm test
$ docker compose up -d

A single test file can be run on its own:

$ node --import tsx --test test/<file>.test.ts

This page is plain static HTML in site/index.html. Vercel serves the site/ directory as-is, with no install and no build (see vercel.json).
